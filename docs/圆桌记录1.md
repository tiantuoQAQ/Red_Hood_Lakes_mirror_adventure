# 一、还会继续踩的 8 个坑（按「最容易做错」排序）

## 坑 1：固定 1/60 步长被 `_process(delta)` 污染
**现象**：所有计时器（无敌 70 帧、冲刺 12 帧、连击窗口 80 帧）用 `delta` 累加，帧率一波动，冲刺距离、无敌时长全变。Godot 默认 60Hz 但 `_process` 的 delta 不保证等于 1/60。
**正确做法**：全局逻辑帧计数器 `var frame: int`，在 `_physics_process` 里 `frame += 1`，所有计时用「帧数」而非秒。`Engine.physics_ticks_per_second = 60`，`Engine.max_physics_steps_per_frame = 1`（防止卡顿后追帧导致一帧跑多步）。速度用「像素/帧」直接乘，不要乘 delta。
**验收**：把 `Engine.time_scale` 设 0.25 和 4.0 各跑一次，冲刺位移、无敌帧数、球形态体力消耗曲线必须完全一致。

## 坑 2：球形态「松开冲刺立刻变回人」被做成「松开后延迟/需落地」
**现象**：用 `is_action_just_released("dash")` 在 `_input` 里处理，或写成「松开后等落地」。网页版是**松开冲刺键当帧立即退出**，且**落地不退出**（贴地悬浮）。
**正确做法**：每帧读 `Input.is_action_pressed("dash")`，为 false 且当前是球 → 当帧 `state = HUMAN`，速度保留（不清零、不减速）。落地检测只用于「贴地悬浮」——`y >= ground_y` 时把 `vy = 0`、`y = ground_y`，**不退出球形态**。
**验收**：空中变球 → 松冲刺 → 当帧截图对比人形；贴地后仍为球，直到松键或体力耗尽。

## 坑 3：球形态「方向键直给速度」被做成加速/惯性
**现象**：用 `move_toward` 或 `lerp` 让方向键平滑加速，导致球形态转向有延迟、合速度不等于 450。
**正确做法**：球形态下 `vx = dir_x * 450`、`vy = dir_y * 450`（有方向键时直接赋值，无方向键时保持上一帧速度或按网页版规则）。**合速度恒为 450**，不是分量各 450。前 5 帧强制 `vy = -450`（覆盖方向键的 y 分量）。进入瞬间 `vx *= 0.4; vy = -450`。
**验收**：斜向 45° 移动时，位移/帧 = 450/√2 ≈ 318.2，不是 450。

## 坑 4：擦弹判定用物理体/Area2D，导致漏判或重复计数
**现象**：用 `Area2D` 的 `body_entered` 做擦弹，子弹高速穿过时漏判；或同一颗子弹每帧都触发，连击暴涨。
**正确做法**：擦弹是**纯数学判定**，每帧遍历所有子弹：`dist = (bullet.pos - player.pos).length()`，`4 < dist <= 30` 且该子弹本帧未擦过（`bullet.grazed_this_frame = false` 标记，或每颗子弹存 `last_graze_frame`）→ 触发一次。判定半径 4 是「命中」，30 是「擦弹环」。
**验收**：一颗子弹从玩家身边匀速掠过，擦弹计数恰好 +1；连击窗口 80 帧内不重复。

## 坑 5：BOSS 血条做成「分段并列条」
**现象**：5 段血条并排显示，或每段独立扣血。
**正确做法**：**整场一根条**。内部维护 `stage`（当前段）和 `hp`（当前段血量）。打空 → `stage += 1` → `hp = max_hp` → 血条视觉上「回满」（可加一个 0.2s 的白色闪回动画）。界面文字 `STAGE {stage}/{total}`，魔姬 total=5，玛丽苏 total=6；未解锁时显示 `STAGE {stage}/?`。
**验收**：打空第一段，血条从 0 瞬间回满，文字从 `STAGE 1/5` 变 `STAGE 2/5`，不是出现第二根条。

## 坑 6：子弹磁吸用 `global_position.direction_to` 每帧重算，导致抖动/过冲
**现象**：280px 内磁吸，用 `direction_to(boss)` 每帧改速度方向，子弹在边界反复横跳，或吸过头穿过 BOSS。
**正确做法**：磁吸是**速度向量插值**：`v = v.lerp((boss.pos - pos).normalized() * speed, k)`，`k` 取小值（如 0.08），且只在 `dist < 280` 时生效。不要改 `speed` 大小，只改方向。边界处用 `dist < 280` 硬开关会有突变，可加 20px 缓冲带做 `k` 渐变。
**验收**：子弹从 300px 外飞向 BOSS，轨迹平滑弯曲，无折线、无抖动。

## 坑 7：顿帧用 `Engine.time_scale = 0` 或 `get_tree().paused = true`
**现象**：命中顿帧 4~10 帧，用全局暂停实现，导致 UI、震屏、粒子也停，或恢复时 delta 突变。
**正确做法**：顿帧只冻结**游戏逻辑帧计数器**：`if hitstop > 0: hitstop -= 1; return`（在 `_physics_process` 开头），渲染、震屏、UI 照常跑。震屏用衰减正弦：`offset = sin(t * freq) * amp * exp(-t * decay)`，独立于逻辑帧。
**验收**：命中瞬间游戏物体静止 4~10 帧，但震屏和血条动画仍在动。

## 坑 8：剧情演出命令用 `await get_tree().create_timer()` 串联，无法跳过/无法与游戏逻辑同步
**现象**：19 种演出命令用 `await` 顺序执行，玩家按键跳过时卡死，或演出期间游戏逻辑仍在跑导致状态错乱。
**正确做法**：演出是**数据驱动的帧脚本**：每条命令带 `duration_frames`，用一个 `story_frame` 计数器推进，`_physics_process` 里 `story_frame += 1`，到点执行下一条。跳过 = `story_frame = 当前命令结束帧`。演出期间游戏逻辑可选择暂停或继续（按网页版规则）。
**验收**：任意时刻按跳过键，演出立即结束且游戏状态正确；演出中帧率波动不影响命令时序。

# 二、手感等价性的 3 个系统性差异

## 差异 1：积分方式——网页版是「先算后移」，Godot 默认「物理体移动」
**问题**：网页版每帧 `pos += v`，位置是纯数值；Godot 用 `CharacterBody2D.move_and_slide()` 会引入碰撞滑动、斜坡投影、`velocity` 被物理引擎改写，冲刺 1020 速度会被墙「削」掉。
**规避**：玩家**不用 `CharacterBody2D`**，用 `Node2D` + 手写 `pos += v`，碰撞用矩形 AABB 手动检测（地面线 y=574 是硬约束）。如果必须用物理体，`motion_mode = MOTION_MODE_FLOATING`，且每帧 `velocity = 手算值`，`move_and_slide()` 后强制 `velocity = 手算值`（不让引擎改）。

## 差异 2：输入采样——网页版是「事件 + 状态」，Godot 是「状态轮询」
**问题**：网页版 `keydown` 事件能捕获「同一帧内按下又松开」，Godot `Input.is_action_just_pressed` 在 `_physics_process` 里可能漏掉（如果按键发生在两个物理帧之间）。8 帧输入缓冲、冲刺起步 3 帧、球形态「按下冲刺」这些对时序敏感。
**规避**：在 `_input(event)` 里捕获 `InputEventKey`/`InputEventMouseButton` 的 pressed/released，写入自己的 `input_buffer` 数组（带帧号），逻辑帧从 buffer 读。鼠标位置用 `get_global_mouse_position()` 每帧采样，但**射击方向在按下瞬间锁定**（网页版是按下时算方向，不是持续跟随）。

## 差异 3：渲染顺序与混合模式——`lighter` 在 Godot 里没有直接对应
**问题**：球形态 6 层特效全用 `lighter`（加法混合），Godot 的 `CanvasItemMaterial` 默认是 `MIX_MODE_MIX`，需要显式设 `blend_mode = BLEND_MODE_ADD`。且 Godot 的 `draw_*` 调用顺序 = 渲染顺序，但 `z_index` 会覆盖。
**规避**：球形态用一个 `Node2D` 的 `_draw()` 里按顺序画 6 层，材质设 `CanvasItemMaterial.blend_mode = BLEND_MODE_ADD`。注意 Godot 的 `draw_circle` 不支持径向渐变，用 `draw_texture` + 预生成的 `GradientTexture2D`（径向），或 `draw_polygon` 分段模拟。旋转弧用 `draw_arc`，冲击波用 `draw_arc` + 透明度衰减。**所有层必须在同一个 `_draw()` 里按顺序调用**，不要拆成多个子节点（z_index 会乱）。

# 三、唯一的调试面板：6 个参数

1. **`frame`（逻辑帧号）**——所有时序问题的基准，对不上就是积分方式错了。
2. **`player.state`（HUMAN/BALL/DASH/INVULN）**——状态机是核心，状态错则一切错。
3. **`player.vx, vy`（当前速度）**——冲刺 1020、球形态合速度 450、滑行 0.72 保留率，一眼看出。
4. **`player.stamina`（体力）**——球形态 -32/s，>20 才能变球，数值对不上就是帧率问题。
5. **`graze_combo` + `courage`（连击/勇气）**——擦弹窗口 80 帧、每 5 连 +0.5 倍、上限 3 倍，验证擦弹逻辑。
6. **`boss.stage / hp / max_hp`**——血条「整场一根条」的核心，验证回满逻辑。

**为什么是这 6 个**：它们覆盖了移植方已踩的 5 个坑（球形态、射击方向、手感、血条）+ 最容易继续踩的时序/擦弹坑。任何一个数值异常，都能直接定位到具体机制。

# 四、最可能「写了但对方仍会理解错」的一处

**原文**（推测在交接文档里）：
> 球形态：在空中 + 按住 W + 按下冲刺 + 体力>20 → 变无敌光球；进入瞬间 vx*=0.4、vy=-450，前 5 帧强制上冲；期间方向键直给速度（合速度 450）、体力 -32/s；落地不退出（贴地悬浮）；松开冲刺立刻变回人；体力耗尽退出；地面上按 W+冲刺只算普通冲刺。

**问题**：这段话信息密度太高，且「按住 W + 按下冲刺」的时序、「方向键直给速度」的语义、「落地不退出」与「松开退出」的优先级，都是歧义点。移植方很可能做成「按 W 变球」或「落地退出」。

**改写建议**（可直接替换）：

```
【球形态 —— 逐帧状态机，必须严格按此实现】

进入条件（每帧检查，全部满足才进入）：
  1. player.on_ground == false（在空中）
  2. Input.is_action_pressed("up")（W 键按住）
  3. Input.is_action_just_pressed("dash")（冲刺键本帧刚按下）
  4. player.stamina > 20
  注意：地面上按 W + 冲刺 → 只触发普通冲刺，不变球。

进入瞬间（当帧执行一次）：
  player.vx *= 0.4
  player.vy = -450
  player.state = BALL
  player.ball_frame = 0

球形态期间（每帧）：
  player.ball_frame += 1
  if player.ball_frame <= 5:
      player.vy = -450          # 前 5 帧强制上冲，忽略方向键 y 分量
  else:
      dir = 方向键输入向量（归一化）
      if dir != 0:
          player.vx = dir.x * 450
          player.vy = dir.y * 450   # 合速度恒为 450，不是分量各 450
      # 无方向键时保持上一帧速度
  player.stamina -= 32 / 60     # 每帧扣，不是每秒扣
  if player.y >= GROUND_Y:
      player.y = GROUND_Y
      player.vy = 0             # 贴地悬浮，不退出球形态

退出条件（每帧检查，任一满足即退出）：
  1. Input.is_action_pressed("dash") == false  → 当帧立即退出，速度保留
  2. player.stamina <= 0                        → 退出
  退出时：player.state = HUMAN，不清零速度，不减速，不落地。

禁止事项：
  - 不要用 move_and_slide()
  - 不要用 delta 累加体力
  - 不要在退出时做任何速度插值
  - 不要用 Area2D 检测落地
```

这样改写后，每一条都是可执行的伪代码，没有歧义空间。
